# デジタル庁デザインシステムを基にした全体UI改善 設計仕様

## 1. 目的

`profile-renewal-cms` 全体のデザインを、デジタル庁デザインシステムの「アクセシビリティファースト」「意味に基づく色と状態」「一貫したタイポグラフィと余白」の考え方を基準に改善する。

TOMOCANのロゴ、オレンジ、写真、ヒーロー、親しみやすい雰囲気は維持する。行政サイトの見た目を模倣するのではなく、既存ブランドに適合するデザインシステムとして再構成する。

## 2. 成功条件

- トップ、プロフィール、スキル、制作実績、ブログ、問い合わせ、404が同じ視覚ルールで構成されている。
- PCとスマートフォンで、情報の優先順位、余白、見出し、CTA、カード、フォームの振る舞いが一貫している。
- 本文、リンク、ボタン、フォーム、フォーカス表示がWCAG 2.2 AA相当の観点で確認されている。
- ロゴ、ブランドオレンジ、写真、ヒーローの泡、短いローディングを残し、現在のサイトだと認識できる。
- microCMS、問い合わせ送信、URL、SEO、構造化データ、ページネーション、検索、カテゴリの既存挙動が維持されている。
- lint、型検査、CSS生成、production build、PC/SPのブラウザ確認が完了している。

正式なJISまたはWCAG適合表明は本作業の対象外とする。実装範囲について確認結果を報告する。

## 3. 非対象

- ロゴ、ヒーロー画像、プロフィール写真、OGP画像の作り直し
- サイト名、実績、経歴、記事、問い合わせ案内などの内容変更
- microCMSスキーマまたは公開データの変更
- URL、ルーティング、metadata、canonical、robots、sitemap、JSON-LDの設計変更
- 問い合わせ送信処理、認証、サーバー構成の変更
- 新しいUIライブラリまたはアニメーションライブラリの導入
- ダークモード、新規ページ、新規機能の追加

## 4. 設計原則

1. ブランドを残し、UIルールを改善する。
2. 色だけで意味や状態を伝えない。
3. すべてをカードにせず、余白、罫線、背景差、見出しで構造を示す。
4. 操作要素には通常、hover、active、focus-visible、disabledの状態を用意する。
5. PC/SPでDOM順序と情報の優先順位を変えない。
6. 動きは理解やブランド表現を助ける範囲に限定する。
7. 既存クラスとコンポーネントをできるだけ再利用し、機能変更を伴う大規模な再構築を避ける。

## 5. 実装アーキテクチャ

共通基盤からページ固有スタイルへ段階的に適用する。

1. `styles/global/_variables.scss` にプリミティブ値とセマンティックトークンを定義する。
2. `styles/foundation/` で本文、リンク、フォーカス、reduced-motionを統一する。
3. `styles/layout/` でヘッダー、フッター、本文幅、ページタイトル、ブログ本文幅を統一する。
4. `styles/object/component/` で見出し、ボタン、リンク、パンくず、一覧、ページネーション、テーブルを統一する。
5. 既存の共通Reactコンポーネントへ状態とアクセシビリティ属性を反映する。
6. `styles/pages/` と各CSS Moduleでページ固有のレイアウトだけを調整する。

新しいランタイム依存は追加しない。SCSSの既存構成とCSS Moduleを維持する。SCSS変更後は `npm run build:css` を実行し、追跡されている生成CSSとsource mapを同期する。

## 6. デザイントークン

### 6.1 色

以下を基準値とする。

| 役割 | 値 | 用途 |
| --- | --- | --- |
| Brand accent | `#f36b0a` | ロゴとの連続性、装飾、強調背景。白い通常文字は載せない |
| Brand strong | `#b54708` | 白文字の主要CTA、リンク文字、主要境界線 |
| Brand strong hover | `#8f3500` | 主要CTAのhover/active |
| Text primary | `#282828` | 見出し、本文 |
| Text secondary | `#666666` | 日付、補足。白背景で通常文字に使用可能 |
| Background | `#fcf6f1` | サイト全体の暖色系背景 |
| Background subtle | `#f5ede7` | セクションの弱い背景差 |
| Surface | `#ffffff` | 必要なカード、フォーム、浮遊要素 |
| Border | `#d8cec7` | 通常境界線 |
| Focus | `#0066cc` | 専用フォーカスリング |
| Error | `#b3261e` | エラー文字、エラー境界線 |

`#f36b0a` と白のコントラスト比は通常文字に不足するため、白文字のボタンには `#b54708` を使う。`#f36b0a` は黒系文字との組み合わせまたは非テキスト装飾に限定する。

フォーカスは `3px solid #0066cc` と白い間隔を組み合わせ、背景色に埋もれない二重構造とする。

### 6.2 タイポグラフィ

- 基本文字: 16px、line-height 1.8
- 記事本文: 17px、line-height 1.9、最大幅760px
- 補助文字: 13px以上、line-height 1.6以上
- ページH1: `clamp(2rem, 4vw, 3rem)`、line-height 1.35
- セクションH2: `clamp(1.75rem, 3vw, 2.25rem)`、line-height 1.4
- カードH3: `clamp(1.25rem, 2vw, 1.5rem)`、line-height 1.5
- 本文の字間は原則として標準値を使い、英語装飾ラベルだけに限定して字間を広げる。
- Robotoと既存の日本語システムフォント構成を維持する。

英語＋日本語見出しは維持する。英語を補助ラベル、日本語を主見出しとして視覚的な優先順位を統一する。

### 6.3 余白、幅、形状

- 余白スケール: 4、8、12、16、24、32、48、64、80、96px
- 一般コンテンツ最大幅: 1120px
- 読み物最大幅: 760px
- PC左右余白: 24px
- タブレット左右余白: 20px
- SP左右余白: 16px
- セクション間隔: PC 80〜96px、SP 56〜64px
- 角丸: 小6px、標準10px、強調16px
- 主要ボタン最小高さ: 48px
- アイコンボタンとSPナビゲーション最小ターゲット: 44×44px

影は浮遊要素とhover時の補助に限定し、標準値を `0 8px 24px rgba(40, 40, 40, 0.08)` とする。通常の情報区切りは罫線と余白を優先する。

## 7. 共通コンポーネント

### 7.1 ヘッダーとナビゲーション

- ロゴ、ナビゲーション項目、外部ブログ、SNS導線を維持する。
- PCヘッダーは最大88px、SPヘッダーは64pxを基準とする。
- ヒーロー上の透明状態と、通常コンテンツ上の読みやすい背景状態を明確にする。
- 現在ページは下線、文字ウェイト、`aria-current="page"` で示す。
- SPメニューボタンは開閉名、`aria-expanded`、`aria-controls`、明確なfocus-visibleを持つ。
- SPメニュー展開時はフォーカス順序、背景スクロール、Escapeでの終了を確認する。
- 外部ブログとSNSは主要ページ群から視覚的に分離する。

### 7.2 見出し

- ページタイトル、セクションH2、カードH3の3階層を基本にする。
- 英語ラベル、和文見出し、装飾線の間隔とサイズを共通化する。
- HTMLの見出しレベルは飛ばさない。見た目のために見出しレベルを変更しない。

### 7.3 ボタンとリンク

ボタン表現は次の3種類に限定する。

1. Primary: `#b54708` 背景、白文字、主要CTA
2. Secondary: 白または透明背景、`#b54708` の文字と境界線、補助CTA
3. Text: 下線付き文字リンク、戻る・補足・本文内遷移

- hover時には色の変化に加えて下線または境界線の変化を使う。
- activeはhoverより濃い状態にする。
- focus-visibleは共通フォーカスリングを使う。
- disabledは色だけでなくカーソルと操作不可状態を反映する。
- 本文リンクは原則として下線付きにする。
- 外部リンクは既存SVGアイコンを再利用し、代替テキストまたは可視ラベルを維持する。

### 7.4 パンくず、ページネーション、ページトップ

- パンくずは14px以上、折り返し可能、現在ページをリンクにしない。
- ページネーションは現在ページを色、境界、`aria-current` で示す。
- ページトップは44×44px以上を確保し、影と移動を控えめにする。

### 7.5 カードと一覧

- 実績とブログは「画像、分類、見出し、概要、補足、導線」の順に統一する。
- カード全体リンクでは、accessible nameから遷移先が理解できる状態を維持する。
- 技術タグとカテゴリは補助情報として表示し、本文より強くしない。
- hover時の浮き上がりは最大2pxとし、reduced-motionでは移動させない。
- プロフィール本文、職歴、資格、記事本文は原則としてカード化せず、余白と区切り線を使う。

### 7.6 フォーム

- ラベル、必須表示、補足、入力欄、エラーを同じフィールドグループに置く。
- 入力欄の最小高さは44px、本文入力欄は十分な初期高さを持たせる。
- エラーは `#b3261e` の文字、境界線、具体的な文言で示す。
- エラー概要と該当フィールドの関連付けを維持または改善する。
- 送信中、成功、失敗の既存状態と送信処理は変更しない。

## 8. ページ別設計

### 8.1 トップ

- ヒーロー画像、似顔絵、TOMOCAN、役割、H1、説明、2つのCTA、泡、Scroll表現を維持する。
- H1と説明文の可読性を高めるため、背景オーバーレイと本文幅を調整する。
- CTAはSPで縦積み、PCで横並びとし、DOM順序を変えない。
- 実績数値は定義リストの構造を維持し、SPでも値とラベルを一度に読める配置にする。
- 実績、スキル、プロフィール、ブログ、問い合わせのセクション間隔と導線位置を統一する。

### 8.2 プロフィール

- 現在の仕事、実務経験、得意領域、仕事の姿勢、資格・実績の順序を維持する。
- 経歴や事実情報はカードを増やさず、定義リスト、罫線、2カラムから1カラムへの自然な変化で整理する。

### 8.3 スキル

- 実務と個人開発の区分、スキルアイコン、説明内容を維持する。
- アイコンの視覚的な大きさを統一し、名称と説明を主役にする。
- PC/SPで項目順を維持し、横スクロールを発生させない。

### 8.4 制作実績

- 一覧では案件種別、サイト種別、期間、タイトル、担当、技術、概要、詳細導線を比較しやすくする。
- 詳細ではタイトルと案件情報を先に示し、概要、課題、制約、担当範囲、判断、成果、対象外の本文を主役にする。
- 任意CMSフィールドが空の場合は、現在と同様にセクションを表示しない。
- 関連実績と問い合わせ導線は本文より弱い階層に置く。

### 8.5 ブログ

- 一覧、検索、カテゴリ、記事詳細で日付、カテゴリ、見出し、概要の表現を統一する。
- 記事本文は最大760px、17px、line-height 1.9を基準にする。
- CMS本文内の見出し、リスト、表、引用、画像、リンクの間隔と可読性を統一する。
- 検索条件、0件状態、ページネーションの意味を明確にする。

### 8.6 問い合わせ

- 受付内容と新規制作依頼を受け付けていない旨を維持する。
- フィールドのまとまり、必須表示、エラー、確認・送信操作を一貫させる。
- ラジオボタンとラベル全体を操作可能な領域として扱う。

### 8.7 404と空状態

- 絵文字に依存しない。
- 状態を説明する見出し、短い説明、次の行動を示すリンクまたはボタンで構成する。

## 9. モーション

- ヒーローの泡は維持する。数と速度は現在以下に抑える。
- ローディングは最大500msの短いフェードとして維持する。
- スクロール出現はフェードと16〜24pxの縦移動へ統一する。
- 標準時間は200〜400msとする。
- 通常hoverでの移動は最大2pxとする。
- 回転、反転、80px移動など、実ページで不要な汎用アニメーション定義は削除または非使用化する。
- `prefers-reduced-motion: reduce` では泡、波、スクロール移動を停止し、コンテンツを最初から表示する。
- reduced-motionでもメニューやフォームの状態が理解できるよう、必要な表示切り替えは即時に行う。

## 10. データフローとエラー処理

- microCMSの取得関数、クエリ、型、キャッシュ、静的生成方法を変更しない。
- 実績・記事・カテゴリ・検索・ページネーションのURLと件数計算を変更しない。
- 問い合わせServer Actionとバリデーション規則を変更しない。
- metadata、canonical、robots、sitemap、JSON-LDを変更しない。
- 既存の空状態、notFound、送信失敗を維持し、視覚表現のみ共通化する。
- UI調整中にエラー処理の欠落を発見した場合は、今回の実装へ混ぜず、別の課題として報告する。

## 11. アクセシビリティ基準

- 通常文字は4.5:1以上、大きな文字と非テキストUIは3:1以上を目標とする。
- すべてのリンク、ボタン、フォーム部品にキーボードで到達できる。
- focus-visibleが背景やhover状態に埋もれない。
- 見出しレベルを飛ばさない。
- 操作対象は原則44×44px以上、主要CTAは高さ48px以上とする。
- 色だけで現在位置、エラー、選択、重要度を示さない。
- 200%拡大時に情報または操作が欠けない。
- 390px幅で意図しない横スクロールを発生させない。
- 画像の既存alt、装飾画像の空alt、ARIAラベルを維持または改善する。
- DOM順序と視覚順序を一致させる。

## 12. 検証計画

### 12.1 自動・コマンド検証

実装完了時に次を実行する。

```powershell
npm run build:css
npm run lint
npm run typecheck
npm run build
```

必要に応じて、UI寸法、トークン、見出し構造、アクセシビリティ属性、reduced-motionを対象にNodeベースの回帰テストを追加する。

### 12.2 ブラウザ検証

PC 1280×900前後とSP 390×844前後で次を確認する。

- `/`
- `/about/`
- `/skill/`
- `/result/`
- `/result/[id]/` の公開実績1件以上
- `/diary/`
- `/diary/[slug]/` の公開記事1件以上
- `/diary/search/?q=Next.js`
- `/diary/category/[id]/`
- `/contact/`
- 存在しないURLによる404

各画面で次を確認する。

- 横スクロール、文字切れ、画像欠け、CTA欠けがない。
- H1が1つで、見出し順序が自然である。
- キーボードでヘッダー、SPメニュー、カード、ページネーション、フォームを操作できる。
- focus-visibleが全操作要素で確認できる。
- reduced-motion時に泡、波、大きな移動が停止する。
- 200%拡大時に情報と操作が欠けない。
- 問い合わせのエラーが色以外でも理解できる。

### 12.3 既存出力の保護確認

- 主要ページのtitle、canonical、robotsを確認する。
- JSON-LDをDOM文字列ではなくJSONとして解析し、既存種別を確認する。
- `/result/` と `/result/p/[current]/`、検索、カテゴリの既存ページネーション挙動を確認する。
- sitemapとrobots.txtの既存方針が維持されていることを確認する。

## 13. 完了条件

次のすべてを満たした時点で完了とする。

1. 共通トークンと全対象ページへの適用が完了している。
2. ブランド、内容、URL、CMS、SEO、送信処理が維持されている。
3. 適度なモーションとreduced-motionが両立している。
4. 自動検証がすべて成功している。
5. PC/SP、キーボード、200%拡大、reduced-motionの実画面確認が完了している。
6. `git status` と差分を確認し、意図しない変更が残っていない。
